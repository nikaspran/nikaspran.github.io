11:T550e,<p>It is not enough for code to simply work. Good code is meant to be easy to understand, and it is much easier to understand code that is readable.</p>
<h2 id="comments-considered-harmful">Comments Considered Harmful</h2>
<p>Traditionally, algorithms have often been explained in <a href="https://github.com/angular-ui/ui-router/blob/3da0a17069e27598c0f9d9164e104dd5ce05cdc6/src/state.js#L1082">large comment blocks</a>. The notion that writing many comments makes code easier to understand is still quite prevalent in the industry. Yet when it comes to code, less is very often more.</p>
<p>Good comments are to the point and explain the why, not the how:</p>
<pre><code class="hljs language-js"><span class="hljs-comment">// bad</span>
$scope.<span class="hljs-property">model</span> = _.<span class="hljs-title function_">extend</span>({}, modelMap); <span class="hljs-comment">// reset $scope.model</span>

<span class="hljs-comment">// good</span>
<span class="hljs-keyword">function</span> <span class="hljs-title function_">partialUpdateReview</span>(<span class="hljs-params">review, publishedAt</span>) {
  <span class="hljs-comment">// <span class="hljs-doctag">TODO:</span> use POST until API supports PUT</span>
  <span class="hljs-keyword">return</span> $http.<span class="hljs-title function_">post</span>(<span class="hljs-string">'/api/reviews/published'</span>, {<span class="hljs-attr">publishedAt</span>: publishedAt});
}
</code></pre>
<p>Good code has to be obvious, and you do not need to explain that which is obvious. Nearly every comment you write is a failure to write clear and understandable code. Good code, simply put, is self-documenting.</p>
<p>This leaves us with explaining the how. One way to make code readable is to have it flow like the natural language, describe the algorithm in a higher level of abstraction. This leaves the implementation open to explore to those who desire details, yet hides it from those who simply wish to get the gist.</p>
<h2 id="fluent-javascript">Fluent JavaScript</h2>
<p>The main goal of writing <a href="http://martinfowler.com/bliki/FluentInterface.html">Fluent interfaces</a> is to end up with code that can be read like natural language, thus removing the need for superficial comments.</p>
<p>That is, instead of this:</p>
<pre><code class="hljs language-js"><span class="hljs-title function_">insertIntoAfter</span>(<span class="hljs-number">2</span>, [<span class="hljs-number">1</span>, <span class="hljs-number">3</span>], <span class="hljs-number">1</span>); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>We have something like this:</p>
<pre><code class="hljs language-js"><span class="hljs-title function_">insert</span>(<span class="hljs-number">2</span>).<span class="hljs-title function_">into</span>([<span class="hljs-number">1</span>, <span class="hljs-number">3</span>]).<span class="hljs-title function_">after</span>(<span class="hljs-number">1</span>); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>The fluent version basically reads like a natural language sentence, which makes it very easy to understand. This is especially useful in functions that take more than a few arguments - the regular way devolves into a soup of obscure parameters, reminiscent of the <a href="http://en.wikipedia.org/wiki/Polish_notation">Polish notation</a>, while the fluent interface remains highly readable at a glance.</p>
<p>Fluent interfaces are nothing groundbreaking. They are, essentially, a form of <a href="http://en.wikipedia.org/wiki/Domain-specific_language">domain-specific languages</a>. In fact, most of BDD style testing libraries use some sort of fluent API. For example:</p>
<ul>
<li><a href="https://github.com/Automattic/expect.js">expect.js</a></li>
</ul>
<pre><code class="hljs language-js"><span class="hljs-title function_">expect</span>(<span class="hljs-variable language_">window</span>.<span class="hljs-property">r</span>).<span class="hljs-property">to</span>.<span class="hljs-title function_">be</span>(<span class="hljs-literal">undefined</span>);
<span class="hljs-title function_">expect</span>({ <span class="hljs-attr">a</span>: <span class="hljs-string">'b'</span> }).<span class="hljs-property">to</span>.<span class="hljs-title function_">eql</span>({ <span class="hljs-attr">a</span>: <span class="hljs-string">'b'</span> })
<span class="hljs-title function_">expect</span>(<span class="hljs-number">5</span>).<span class="hljs-property">to</span>.<span class="hljs-property">be</span>.<span class="hljs-title function_">a</span>(<span class="hljs-string">'number'</span>);
<span class="hljs-title function_">expect</span>([]).<span class="hljs-property">to</span>.<span class="hljs-property">be</span>.<span class="hljs-title function_">an</span>(<span class="hljs-string">'array'</span>);
<span class="hljs-title function_">expect</span>(<span class="hljs-variable language_">window</span>).<span class="hljs-property">not</span>.<span class="hljs-property">to</span>.<span class="hljs-property">be</span>.<span class="hljs-title function_">an</span>(<span class="hljs-title class_">Image</span>);
</code></pre>
<ul>
<li><a href="http://jasmine.github.io/2.2/introduction.html">Jasmine</a> matchers</li>
</ul>
<pre><code class="hljs language-js"><span class="hljs-title function_">expect</span>(a).<span class="hljs-title function_">toBe</span>(b);
<span class="hljs-title function_">expect</span>(a).<span class="hljs-property">not</span>.<span class="hljs-title function_">toBe</span>(<span class="hljs-literal">null</span>);

obj.<span class="hljs-property">should</span>.<span class="hljs-property">have</span>.<span class="hljs-title function_">property</span>(<span class="hljs-string">'path'</span>);
</code></pre>
<p>The prevalence of these types of interfaces in places where readability is extremely important (unit tests can be considered a type of documentation) is a signal that this works well in practice.</p>
<h2 id="sold-what-now">Sold, what now?</h2>
<p>Even if you are not writing public facing libraries, a touch of readability in internal code never hurt anyone. Writing fluent APIs and functions is actually relatively straightforward, if a little clunky even in vanilla JavaScript.</p>
<h3 id="vanilla-javascript">Vanilla JavaScript</h3>
<p>One idea of implementing fluent functions in vanilla JS relies on returning objects with a single property (that is, the next function to chain while using it) while relying on closures to hold intermediate parameters.</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">function</span> <span class="hljs-title function_">insert</span>(<span class="hljs-params">value</span>) {
  <span class="hljs-keyword">return</span> {<span class="hljs-attr">into</span>: <span class="hljs-keyword">function</span> (<span class="hljs-params">array</span>) {
    <span class="hljs-keyword">return</span> {<span class="hljs-attr">after</span>: <span class="hljs-keyword">function</span> (<span class="hljs-params">afterValue</span>) {
      array.<span class="hljs-title function_">splice</span>(array.<span class="hljs-title function_">indexOf</span>(afterValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);
      <span class="hljs-keyword">return</span> array;
    }};
  }};
}

<span class="hljs-title function_">insert</span>(<span class="hljs-number">2</span>).<span class="hljs-title function_">into</span>([<span class="hljs-number">1</span>, <span class="hljs-number">3</span>]).<span class="hljs-title function_">after</span>(<span class="hljs-number">1</span>); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>This is actually not too bad, but it can be a little overwhelming due to so many <code>function</code> and <code>return</code> keywords everywhere.</p>
<p>ES6 lets us write this in a more concise way, at the cost of introducing some crazy punctuation:</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">let</span> <span class="hljs-title function_">insert</span> = (<span class="hljs-params">value</span>) => ({<span class="hljs-attr">into</span>: <span class="hljs-function">(<span class="hljs-params">array</span>) =></span> ({<span class="hljs-attr">after</span>: <span class="hljs-function">(<span class="hljs-params">afterValue</span>) =></span> {
  array.<span class="hljs-title function_">splice</span>(array.<span class="hljs-title function_">indexOf</span>(afterValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);
  <span class="hljs-keyword">return</span> array;
}})});

<span class="hljs-title function_">insert</span>(<span class="hljs-number">2</span>).<span class="hljs-title function_">into</span>([<span class="hljs-number">1</span>, <span class="hljs-number">3</span>]).<span class="hljs-title function_">after</span>(<span class="hljs-number">1</span>); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>Another, slightly more limiting option is to forego function composition entirely and just go with a single parameters object and one function that can handle it all:</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">function</span> <span class="hljs-title function_">insert</span>(<span class="hljs-params">params</span>) {
  <span class="hljs-keyword">var</span> array = params.<span class="hljs-property">into</span>,
      value = params.<span class="hljs-property">value</span>,
      afterValue = params.<span class="hljs-property">after</span>;

  array.<span class="hljs-title function_">splice</span>(array.<span class="hljs-title function_">indexOf</span>(afterValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);
  <span class="hljs-keyword">return</span> array;
}

<span class="hljs-title function_">insert</span>({<span class="hljs-attr">value</span>: <span class="hljs-number">2</span>, <span class="hljs-attr">into</span>: [<span class="hljs-number">1</span>, <span class="hljs-number">3</span>], <span class="hljs-attr">after</span>: <span class="hljs-number">1</span>}); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>Writing simple fluent interfaces is clearly possible even in plain old JavaScript. If we're only creating a few fluent functions here and there, it's probably the best approach. However, if we were to adopt the fluent interface as a common pattern in a codebase, we'd quickly run into the same readability issues we'd like to avoid - while easy to read for consumers, the vanilla JS ways of producing fluent interfaces are not obvious at first glance.</p>
<h3 id="implementing-a-library-for-fluency">Implementing a library for fluency</h3>
<p>How might a library for creating fluent interfaces look like? While there are a couple of possible approaches, the main idea behind them would be to offer some sort of builder which would produce a segmented fluent function. Let us first consider how this might be achieved in the future.</p>
<h4 id="ideal-interface-for-fluent-function-creation">Ideal interface for fluent function creation</h4>
<p>Arguably, the ideal interface for creating fluent interfaces would itself be fluent. It should also self-document how to use the created function. In other words, it would look something like this:</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">let</span> insert = <span class="hljs-title function_">fluentInterface</span>()
  .<span class="hljs-title function_">insert</span>(<span class="hljs-string">'value'</span>).<span class="hljs-title function_">into</span>(<span class="hljs-string">'array'</span>).<span class="hljs-title function_">after</span>(<span class="hljs-string">'otherValue'</span>)
  .<span class="hljs-title function_">_implementedBy</span>(<span class="hljs-keyword">function</span> (<span class="hljs-params">{value, array, otherValue}</span>) {
    array.<span class="hljs-title function_">splice</span>(array.<span class="hljs-title function_">indexOf</span>(otherValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);
    <span class="hljs-keyword">return</span> array;
  });
</code></pre>
<p>Here, we'd be using named arguments (which might have some sort of validation attached to them, if so desired) and ES6 <a href="https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Destructuring_assignment#Object_destructuring">Object Destructuring</a> to get those into our implementation function. The second line is both a spec for the builder and documentation for the users of this fluent function.</p>
<h4 id="using-es6-proxy">Using ES6 Proxy</h4>
<p>The <a href="https://developer.mozilla.org/en/docs/Web/JavaScript/Reference/Global_Objects/Proxy">Proxy</a> object in ES6 is very promising in this regard. It is, however, not ready for any kind of real usage just yet. There is a shim called <a href="https://github.com/tvcutsem/harmony-reflect">harmony-reflect</a>, but even that at the time of writing this post is mostly supported via browser flags.</p>
<p>In short, the <code>Proxy</code> object allows us to define what happens when a property is accessed, and intercept that with some custom behavior. In our case, we can simply store the property that was called as the new segment name. Here's how that might look:</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">function</span> <span class="hljs-title function_">fluentInterface</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">let</span> parameterSpec = {},
    builder = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Proxy</span>({}, {
      <span class="hljs-attr">get</span>: <span class="hljs-keyword">function</span> (<span class="hljs-params">target, segmentFunction</span>) {
        <span class="hljs-keyword">return</span> segmentFunction === <span class="hljs-string">'_implementedBy'</span> ? _implementedBy : <span class="hljs-keyword">function</span> (<span class="hljs-params"></span>) {
          parameterSpec[segmentFunction] = <span class="hljs-title class_">Array</span>.<span class="hljs-title function_">from</span>(<span class="hljs-variable language_">arguments</span>);
          <span class="hljs-keyword">return</span> builder;
        };
      }
    });
  <span class="hljs-comment">/*... implementation ...*/</span>
  <span class="hljs-keyword">return</span> builder;
}

<span class="hljs-title function_">fluentInterface</span>().<span class="hljs-property">insert</span> <span class="hljs-comment">// returns function that adds its arguments to the parameterSpec</span>

<span class="hljs-title function_">fluentInterface</span>().<span class="hljs-title function_">insert</span>(<span class="hljs-string">'value'</span>) <span class="hljs-comment">// returns builder</span>
<span class="hljs-comment">// parameterSpec === {insert: ['value']}</span>
</code></pre>
<p>While the full implementation of the ideal interface in ES6 is beyond the scope of this post, my attempts can be explored in the initial commits of <a href="https://github.com/nikaspran/fluent.js/tree/a00b9d6ba7c388fa09fa5e69cf21e562e7c8699b">this repository</a>, specifically the files <a href="https://github.com/nikaspran/fluent.js/blob/a00b9d6ba7c388fa09fa5e69cf21e562e7c8699b/fluent-obj.js">fluent-obj.js</a> and <a href="https://github.com/nikaspran/fluent.js/blob/a00b9d6ba7c388fa09fa5e69cf21e562e7c8699b/fluent-arr.js">fluent-arr.js</a>.</p>
<h4 id="lest-we-forget-the-present">Lest we forget the present..</h4>
<p>It <a href="https://github.com/tvcutsem/harmony-reflect/issues/8">seems</a> there is no simple way to implement the ideal builder interface under ES5. There is always the possibility of transpiling (a la <a href="https://facebook.github.io/jsx/">JSX</a>), but that would most likely not be worth the trouble, unless creating an extraordinary amount of fluent functions.</p>
<p>All is not lost, however, as with some lenience in the permitted builder interface we can still arrive at something both readable and very backwards compatible.</p>
<h2 id="introducing-fluentjs">Introducing <a href="https://github.com/nikaspran/fluent.js">fluent.js</a></h2>
<p>And so a few days ago I came up with a tiny JavaScript library called <a href="https://github.com/nikaspran/fluent.js">fluent.js</a>. It's meant to be a simple solution for building fluent interfaces en masse. Here's the interface of the builder:</p>
<pre><code class="hljs language-js"><span class="hljs-keyword">var</span> fluent = <span class="hljs-built_in">require</span>(<span class="hljs-string">'fluent.js'</span>);

<span class="hljs-keyword">var</span> insert = <span class="hljs-title function_">fluent</span>({
  <span class="hljs-attr">insert</span>: <span class="hljs-string">'*'</span>,
  <span class="hljs-attr">into</span>: <span class="hljs-string">'[]'</span>,
  <span class="hljs-attr">after</span>: <span class="hljs-string">'*'</span>
}, <span class="hljs-keyword">function</span> <span class="hljs-title function_">implementedBy</span>(<span class="hljs-params">value, array, otherValue</span>) {
  array.<span class="hljs-title function_">splice</span>(array.<span class="hljs-title function_">indexOf</span>(otherValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);
  <span class="hljs-keyword">return</span> array;
});

<span class="hljs-title function_">insert</span>(<span class="hljs-number">2</span>).<span class="hljs-title function_">into</span>([<span class="hljs-number">1</span>, <span class="hljs-number">3</span>]).<span class="hljs-title function_">after</span>(<span class="hljs-number">1</span>); <span class="hljs-comment">//[1, 2, 3]</span>
</code></pre>
<p>Not perfect, but it resembles the ideal interface enough that I consider it usable. It is currently able to extend existing objects too, which would look something like this:</p>
<pre><code class="hljs language-js"><span class="hljs-title function_">fluent</span>({
  <span class="hljs-attr">with</span>: <span class="hljs-string">'*'</span>,
  <span class="hljs-attr">after</span>: <span class="hljs-string">'*'</span>
}, <span class="hljs-keyword">function</span> <span class="hljs-title function_">handler</span>(<span class="hljs-params">value, otherValue</span>) {
  <span class="hljs-keyword">var</span> copy = <span class="hljs-variable language_">this</span>.<span class="hljs-title function_">slice</span>(<span class="hljs-number">0</span>);
  copy.<span class="hljs-title function_">splice</span>(copy.<span class="hljs-title function_">indexOf</span>(otherValue) + <span class="hljs-number">1</span>, <span class="hljs-number">0</span>, value);

<p>There's more to be done:</p>
<ul>
<li>
<p><strong>Argument validation</strong> - from required and optional arguments, to some sort of rudimentary type validation, a lot can be done here to facilitate solid API design with little effort.</p>
</li>
<li>
<p><strong>Browser build</strong> - the library is currently Node.js only, but it would be trivial to create a build for the browser. Since the implementation is relatively straightforward, it should support pretty much anything, even the last few remaining IE6s running on potatoes.</p>
</li>
<li>
<p><strong>Branching segments</strong> - this might require altering the interface a little bit, but a nice feature would be to support alternate branches for fluent functions, with different implementations backing them. For example:</p>

<h2 id="in-place-of-a-summary">In place of a summary</h2>
<p>Writing clean and readable code doesn't have to be difficult. While fluent interfaces might take a little bit of work to get right, they are an important tool in improving readability. Most importantly, clean code is supposed to be fun to both write and read. What would an entirely fluent program look like? Could it be read like prose, essentially a high level description of the problem being solved?</p>
