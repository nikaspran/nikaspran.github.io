11:T2f4d,<p>As tradition dictates, this post <em>should</em> start with the obligatory quote
about the two hard things in computer science. Instead, to keep things DRY,
let's just assume we've all already thought of it anyway.</p>
<p>Have you ever come across a 127 line function that does a bunch of computation,
calls multiple endpoints, uses all sorts of asynchronous flows and such and
is called <code>handleClick</code>? Of course, since all programming is a deadly dance with irony,
the only place it appears to be used has nothing to do with clicking anything.
So you sigh heavily, roll up your sleeves and set aside the next few hours to
figure out what it actually does.</p>
<p>Every large code base contains these poor ill-named functions.
With names such as <code>onClick</code>, <code>onLoad</code>, <code>onInit</code>, <code>handleImageLoad</code>, <code>handleChanged</code>, <code>handleEnter</code>,
it's always like a little murder mystery you get to solve.
Except the victim is your sanity and the suspect left the company 2 years ago.</p>
<p>The laziest method names are those that spell out <em>how they're used</em>. They often
don't convey any significant information and could mostly be left out entirely.
Instead, methods should named for <em>what they do</em>. You should never have
to read a function body unless you care about how it does what it does.</p>
<h2 id="so-whats-wrong-with-handlesomethings">So what's wrong with <code>handleSomething</code>s?</h2>
<h3 id="they-hide-the-high-level-structure">They hide the high-level structure</h3>
<p>I believe some actual code makes the point much better than I ever could.
Can you tell what this class does?</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">class</span> <span class="hljs-title class_">Mystery</span> {
  <span class="hljs-title function_">handleDragEnter</span>(<span class="hljs-params"></span>) {
    <span class="hljs-comment">// ...  </span>
  }
  <span class="hljs-title function_">handleDragLeave</span>(<span class="hljs-params"></span>) {
    <span class="hljs-comment">// ...</span>
  }
}
</code></pre>
<p>If you can, I regret to tell you that the <a href="https://en.wikipedia.org/wiki/One_Million_Dollar_Paranormal_Challenge">One Million Dollar Paranormal Challenge</a>
has unfortunately been cancelled and you might have missed out on some serious cash.
How about this one?</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">class</span> <span class="hljs-title class_">Mystery</span> {
  <span class="hljs-title function_">showDropZone</span>(<span class="hljs-params"></span>) {
    <span class="hljs-comment">// ...  </span>
  }
  <span class="hljs-title function_">hideDropZone</span>(<span class="hljs-params"></span>) {
    <span class="hljs-comment">// ...</span>
  }
}
</code></pre>
<p>Much easier, right? It is of course an excerpt from a component for uploading files.
The method names themselves hint at the broader structure and meaning of the code
surrounding them.</p>
<p>Naming methods for what they do is crucial for quickly scanning modules and components
and for actually finding what you care about.</p>
<h3 id="they-tell-you-nothing">They tell you nothing</h3>
<p>Say we're making an awesome slideshow gallery with preloading
(since we're rolling our own implementation instead of using <em>ReactReduxImageSlider.js</em>,
this scenario is somehow set in 2007).
We need to know when our images have finished preloading so that we can mark them as viewable.
So we go ahead and prototype out the following:</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">function</span> <span class="hljs-title function_">onLoad</span>(<span class="hljs-params">image</span>) {
  viewableImages.<span class="hljs-title function_">push</span>(image);
}

image.<span class="hljs-property">onload</span> = <span class="hljs-function">() =></span> <span class="hljs-title function_">onLoad</span>(image);
</code></pre>
<p>So here we are. We've just started implementing something and we've already wasted
12 characters. <em>Of course</em> whatever we assign to <code>onload</code> will happen when the image loads.
We don't need to repeat ourselves. Instead, we should let the reader know what happens when the image loads:</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">function</span> <span class="hljs-title function_">markAsViewable</span>(<span class="hljs-params">image</span>) {
  viewableImages.<span class="hljs-title function_">push</span>(image);
}

image.<span class="hljs-property">onload</span> = <span class="hljs-function">() =></span> <span class="hljs-title function_">markAsViewable</span>(image);
</code></pre>
<p>We should always strive to make our code self explanatory
(I've waged my little war on <a href="/javascript/2015/04/26/fluent-javascript/#comments-considered-harmful">pointless comments</a>
for a while now). Naming functions after the hooks they plug into does little to explain intent.</p>
<h3 id="they-prevent-reusability">They prevent reusability</h3>
<p>Say you've gone ahead and named some method <code>handleClick</code>. It's very simple -
all it does is toggle a dropdown. All is good, until one night three months later
you suddenly wake up drenched in cold sweat, single thought in mind - <em>people have keyboards</em>!
You rush to your workstation, swat away the empty coffee cups and pizza boxes,
open up your favorite editor and start implementing... <code>handleEnter</code>?</p>
<p><em>This would never happen</em>, you say, <em>I would rename it</em>, you add. You're right,
but since it's been three months already you have to figure out if it's being used somewhere
already, and <em>oh it's used 17 times in the template</em> and your editor does not support
cross-file refactoring and now you have to spend 10 minutes just renaming things,
like some sort of savage.</p>
<p>Instead, had you named the method <code>toggleDropdown</code>, you would have saved yourself
the effort and made it self-explanatory. Then all you would have had to deal with was
setting up the event handler and looking up the keycodes and <em>oh look it's 6am already</em>.</p>
<h3 id="theyre-often-flat-out-wrong">They're often flat out wrong</h3>
<p>When confronted with the previous scenario, some people choose a path other than refactoring.
In an almost humanitarian effort to empower blocks of code,
they push their poor methods to do <em>more</em>.</p>
<pre><code class="hljs language-javascript">toggler.<span class="hljs-property">onkeydown</span> = handleClick; <span class="hljs-comment">// sheer madness</span>
</code></pre>
<p>Things change, sometimes drastically (the <em>true</em> hard problem in computer science).
Business logic changes, methods get moved around, blocks of code vanish, functions get reused.
If you name a function for how it gets called, you're anchoring your code to a moment in time.
Any time you change your flow or requirements, you'll likely have to rename the method as well.</p>
<p>Outdated function names are worse than outdated comments -
the latter at least don't make it to stack traces.</p>
<h3 id="they-kill-single-responsibility">They kill single responsibility</h3>
<p>Methods with generic names tend to become a gathering bin for all sorts of random
code which is rarely related. It's much easier to justify
putting an HTTP request into a function called <code>onLoad</code> rather than one called
<code>showMenu</code>.</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">function</span> <span class="hljs-title function_">onLoad</span>(<span class="hljs-params"></span>) {
  menu.<span class="hljs-title function_">show</span>();
  <span class="hljs-title function_">fetch</span>(<span class="hljs-string">'settings'</span>, ...); <span class="hljs-comment">// A-OK!</span>
}

<span class="hljs-keyword">function</span> <span class="hljs-title function_">showMenu</span>(<span class="hljs-params"></span>) {
  menu.<span class="hljs-title function_">show</span>();
  <span class="hljs-title function_">fetch</span>(<span class="hljs-string">'settings'</span>, ...); <span class="hljs-comment">// uhh, is this really the right place for this?</span>
}
</code></pre>
<p>The better alternative is to describe the flow in
higher-level steps, such as <code>showMenu()</code> and <code>loadSettings()</code>. These can then be
grouped under even higher-level functions such as <code>initAndDisplaySettingsMenu()</code>, i.e.:</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">function</span> <span class="hljs-title function_">initAndDisplaySettingsMenu</span>(<span class="hljs-params"></span>) {
  <span class="hljs-title function_">loadSettings</span>();
  <span class="hljs-title function_">showMenu</span>();
}
</code></pre>
<p>What if we need to do more in this method? Say we need to also log a view.
Will the new name be <code>initAndDisplaySettingsMenuAndReportView()</code>?
This doesn't seem like the right approach. Instead, we should think about whether this
method is at the right level of abstraction. Perhaps it should then be called
something more generic, like <code>loadComponent()</code>. It is OK to have generic names.
They just need to describe the correct thing - what the method does, not how it's called.</p>
<h2 id="caveat-external-interfaces">Caveat: external interfaces</h2>
<p>There is one place where naming functions for how they get called is completely
acceptable and even recommended - external interface hooks.</p>
<p>For example, take Angular components. There's a way to one-way bind to an outside
expression, exposing an interface:</p>
<pre><code class="hljs language-javascript">angular.<span class="hljs-title function_">component</span>(<span class="hljs-string">'myButton'</span>, {
  <span class="hljs-attr">bindings</span>: { <span class="hljs-attr">onClick</span>: <span class="hljs-string">'&#x26;'</span> },
  <span class="hljs-title function_">controller</span>(<span class="hljs-params"></span>) {},
  <span class="hljs-attr">template</span>: <span class="hljs-string">`
    &#x3C;button type="button" ng-click="$ctrl.onClick()">My Button&#x3C;/button>
  `</span>
});
</code></pre>
<pre><code class="hljs language-html"><span class="hljs-tag">&#x3C;<span class="hljs-name">my-button</span> <span class="hljs-attr">on-click</span>=<span class="hljs-string">"$ctrl.finishEditing()"</span>></span><span class="hljs-tag">&#x3C;/<span class="hljs-name">my-button</span>></span>
</code></pre>
<p>External interfaces are there to be consumable, so being as clear and obvious as
possible about how they behave is the best strategy here.</p>
<p>Notice that even though we use <code>onClick()</code> for the outside interface name, we're
still naming our actual business logic appropriately
(<code>finishEditing</code>, rather than <code>handleClick</code> or something like that).</p>
<h2 id="a-rose-by-any-other-name">A rose by any other name...</h2>
<p>... misleads and wastes the reader's time! Understanding code would likely still be
an exercise in silent anger even if everything was labelled perfectly. Meanwhile,
the best we can do is make our code as explicit as possible -
at least if we explain ourselves, they might not throw away the madhouse keys.</p>
<h3 id="update-common-counter-arguments">Update: common counter arguments</h3>
<ul>
<li>
<p><strong>Causation <em>is</em> the most important part of a handler so it <em>should</em> be named for when it's called.</strong></p>
<p>This ignores the fact that all handlers still have to be bound to actual events somewhere.
You don't actually lose this association but you do lose the ability to explain
and annotate your code, with code.</p>
<p>As <em>@hnrysmth</em> <a href="https://twitter.com/hnrysmth/status/803323867687243776">pointed out</a>,
<code>handler</code> naming is kind of like <a href="https://en.wikipedia.org/wiki/Hungarian_notation">Hungarian Notation</a>
for methods. In both cases, it is a solution better achieved through tooling
rather than code.</p>
</li>
